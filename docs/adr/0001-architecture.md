# ADR 0001. Архитектура wb-telegram

Статус: принято. Документ обновляется на месте при изменении решений; новые ADR
не заводятся.

## Контекст

Домашний контроллер Wiren Board (WB8, arm64, Debian bullseye, релиз wb-2606).
Нужен Telegram-бот, через который несколько членов семьи отправляют команды
дому и получают уведомления от правил wb-rules. Команды и пользователи должны
настраиваться в штатном веб-интерфейсе контроллера, без правки файлов и без
пересборки бота.

Требования:

- минимум зависимостей: `github.com/go-telegram/bot` и
  `github.com/eclipse/paho.mqtt.golang`, в тестах — `github.com/mochi-mqtt/server/v2`
  и `go.uber.org/mock`;
- всё, что встраивается в экосистему Wiren Board, — строго по её правилам:
  MQTT Conventions, стандарты WB-STD-001/002, форма через `wb-mqtt-confed`,
  debian-пакет и сборка как у Go-пакетов WB;
- одна модель доступа: у команды список людей, которым она доступна; пустой
  список — всем. Ролей и групп нет;
- токен бота не должен попадать ни в браузер, ни в журнал.

## Решения

### 1. Бот — тонкий транспорт, логика в wb-rules

Бот не знает, что делает команда. Каждая команда из настроек — отдельный
контрол `cmd_<имя>` устройства `telegram_bot`; вызов публикуется в него JSON-ом:

```json
{"id":"<update_id>","ts":<unix-время публикации>,"user":"<имя из настроек>","args":"<текст после команды>"}
```

`id` — `update_id` Telegram (уникален), `ts` — момент публикации ботом, а не
`message.date`: возраст сообщения бот проверяет сам, а модуль правил по `ts`
отличает свежий вызов от повторённого retained-значения.

Правила отвечают записью в контрол `send` (`/devices/telegram_bot/controls/send/on`):

- строка (не JSON-объект) — всем пользователям с «Системные уведомления»;
- `{"text","to":[имена]}` — названным людям, флаг уведомлений не учитывается;
- `{"text","reply_to":"<id>"}` — автору вызова; `reply_to` важнее `to`;
- поле `id` игнорируется ботом — модуль правил добавляет его, чтобы одинаковые
  сообщения подряд не склеивались.

Текст отправляется без разметки, длиннее 4096 символов обрезается с «…»;
после доставки текст публикуется в `controls/send` как последнее сообщение.

Встроенное поведение бота: `/start`, `/help` и обычный текст — список доступных
команд; незнакомый chat_id — «Нет доступа, ваш chat_id: N»; недоступная или
несуществующая команда — «Неизвестная команда.» и список; команда старше
`reply_timeout_s` по `message.date` не выполняется («устарела»); нет связи с
MQTT — «Контроллер недоступен, команда не выполнена», вызов не откладывается;
нет ответа с `reply_to` за `reply_timeout_s` — «ответа от правил нет».

Работу с протоколом в правилах скрывает модуль wb-rules `telegram`
(`onCommand`, `cmd.reply`, `send`, `sendTo`), он же отсекает повторы (см. п. 8).

Почему: правила wb-rules уже имеют доступ ко всем устройствам дома; новая
команда — строка в настройках и правило, код бота не меняется.

### 2. MQTT Conventions напрямую на paho, без `wbgong`

Go-сервисы Wiren Board (`wb-rules`, `wb-mqtt-confed`) используют
`github.com/wirenboard/wbgong`. По его коду это только интерфейсы и загрузчик
Go-плагина (`plugin.Open`): все 16 рабочих конструкторов (MQTT-клиент, драйвер,
локальное устройство, атомарная запись файла и т. д.) берутся через `plug.Lookup`
из бинарного `wbgo.so`. Исходник плагина не опубликован, `.so` собирает
CI Wiren Board, каждый пакет кладёт свою копию, а Go-плагин требует точного
совпадения версии Go, флагов сборки и зависимостей, CGO и кросс-компилятора.

Решение: пакет `internal/wbdevice` сам реализует MQTT Conventions на
`paho.mqtt.golang`: `meta` устройства и контролов, retained-значения, подписка на
`/on`, LWT `meta/error = "r"`, `""` после готовности, авто-переподключение с
повторной публикацией состояния и переподпиской, уборка устройства. Брокер —
unix-сокет mosquitto, если он есть, иначе `tcp://localhost:1883`, как у сервисов WB;
флаг `-broker` переопределяет. Бинарь статический, `CGO_ENABLED=0`.

### 3. Telegram — `github.com/go-telegram/bot`

Официальной Go-библиотеки у Telegram нет (TDLib — C++/MTProto, избыточен).
Сравнение на 2026-10-01 (актуальный Bot API — 10.3):

| Библиотека | ★ | Последний релиз | Bot API | Зависимости | Итог |
|---|---|---|---|---|---|
| go-telegram-bot-api/telegram-bot-api | 6.4k | 2021-12 | старый | — | заброшена |
| tucnak/telebot | 4.6k | v3 2024-06, v4 beta | 10.1 (v4) | viper, yaml | нет стабильного свежего релиза |
| **go-telegram/bot** | 1.8k | **v1.27.0, 2026-09-11** | **10.3** | **нет** | **выбрана** |
| mymmrac/telego | 1.1k | 2026-08-29 | 10.3 | fasthttp, sonic | тяжёлые зависимости |
| PaulSonOfLars/gotgbot | 0.7k | только rc | 10.3 | — | вечный release candidate |

Используются long polling (`allowed_updates: ["message"]`), `WithServerURL`
(тесты против `httptest.Server`), обработчик ошибок. Очереди, лимитов и
обработки 429 для отправки библиотека не даёт — это слой `internal/telegram`:
очередь на 100 сообщений с выбросом самых старых при переполнении, не больше
1 сообщения/с в чат и 30/с всего, ожидание `retry_after` на 429, маскирование
токена в ошибках (URL Bot API содержит токен).

Таймауты соединения с Bot API задаются в форме: «Таймаут подключения к Telegram»
(TCP и TLS-рукопожатие, по умолчанию 30 с, 5–120) и «Таймаут опроса Telegram»
(long polling, по умолчанию 30 с, 1–50). Собственного HTTP-клиента нет:
в штатную опцию библиотеки `bot.WithHTTPClient(pollTimeout, client)` передаётся
`http.Client` со стандартным транспортом (`http.DefaultTransport.Clone()`), у
которого выставлены таймауты подключения и рукопожатия; общий таймаут запроса —
подключение + опрос + 10 с. Причина: стандартные 10 с на TLS-рукопожатие
недостаточны, когда провайдер замедляет Telegram (на контроллере рукопожатие с
`api.telegram.org` длилось ~19,5 с, и бот не подключался).

Символы вне базовой плоскости Unicode (эмодзи) wb-rules (движок Duktape)
отдаёт в CESU-8 — суррогатной парой из двух трёхбайтовых последовательностей.
Бот пересобирает их в UTF-8 до разбора сообщения из `send`, иначе Telegram
показал бы «�».

### 4. Токен вне конфига, крючки формы

`wb-mqtt-confed` пишет конфиг через `WriteFileAtomic(..., 0777)` и отдаёт его
содержимое в браузер. Поэтому токен живёт отдельно — `/etc/wb-telegram/token`,
0600, каталог 0700 — и пишется только самим бинарём.

Схема формы подключает крючки `toJSON: ["/usr/bin/wb-telegram", "-to-json"]` и
`fromJSON: ["/usr/bin/wb-telegram", "-from-json"]`:

- `-to-json` получает содержимое конфига на stdin, отдаёт форму с пустым
  `token`, снятым `delete_token` и read-only статусом «Задан / Не задан». Файл
  токена не читается никогда — проверяется только его наличие;
- `-from-json` получает форму на stdin, проверяет то, что схемой не выразить
  (уникальность имён пользователей, chat_id и команд, ссылки команд на
  существующих пользователей, формат токена, одновременные «новый токен» и
  «удалить токен»), затем последним шагом атомарно пишет (temp 0600 → rename)
  или удаляет токен и печатает конфиг без `token`, `delete_token` и
  `token_status`. Ненулевой код выхода — confed ничего не пишет и не
  перезапускает сервис, UI показывает «Ошибка записи», причина (stderr) — в
  `journalctl -u wb-mqtt-confed`. Обратного канала «ошибка → поле» у confed нет.

Токен не пишется в журнал ни на каком уровне.

### 5. Старт, остановка, коды выхода, уборка устройства

| Ситуация | Действие | Код | systemd |
|---|---|---|---|
| `enabled: false` | журнал, уборка устройства | 0 | inactive |
| нет файла токена | журнал, уборка устройства | 0 | inactive |
| Telegram вернул 401 | журнал, уборка устройства | 0 | inactive |
| конфиг на диске не читается или не проходит проверку | журнал с причиной | 1 | failed после попыток `Restart=on-failure` |
| всё в порядке | работа | — | active |

Уборка — пустые retained-сообщения во все найденные `meta` и контролы
устройства. Включение обратно — запись формы: confed делает
`systemctl restart`, который запускает и остановленный юнит.

При старте бот публикует устройство, убирает контролы удалённых команд,
подписывается на `send/on` и только после этого снимает `meta/error`;
`deleteWebhook` и `setMyCommands` со `scope: chat` для каждого пользователя
(каждый видит в меню только доступные ему команды) повторяются с паузой 1 → 60 с
до успеха.

SIGTERM/SIGINT: компоненты останавливаются в обратном порядке — ядро, затем
опрос Telegram и досылка очереди (до 5 с), затем устройство с `meta/error = "r"`;
код выхода 0. Устройство остаётся в веб-интерфейсе с пометкой ошибки до
следующего старта.

### 6. Устройство кода

- Всё в `internal/`: это приложение, а не библиотека, публичного API нет.
- Пакеты: `app` (жизненный цикл), `config` (конфиг, проверки, токен, крючки
  формы), `wbdevice` (MQTT Conventions), `telegram` (Bot API, очередь, лимиты),
  `retry` (паузы повторов 1 → 60 с, общие для `telegram` и `bot`), `bot` (ядро).
- Жизненный цикл: `Component { Run(ctx) error; Stop() error }`, необязательный
  `GracefulComponent { Shutdown(ctx) error }`; запуск в порядке регистрации
  (`wbdevice` → `telegram` → `bot`), остановка в обратном; `signal.NotifyContext`
  (SIGTERM, SIGINT); при ошибке старта уже запущенные компоненты
  останавливаются; ошибки остановки собираются `errors.Join`. Компонент может
  попросить остановить приложение (`Terminate`) — так Telegram-клиент сообщает о 401.
- Конструкторы: `New(обязательное, opts ...Option)`, значения по умолчанию,
  последняя опция побеждает, `options.Validate()` перед сборкой.
- Ошибки: в каждом пакете один экспортируемый `*Error` с неэкспортируемым видом
  ошибки и сентинелы для `errors.Is` (`telegram.ErrUnauthorized`,
  `telegram.ErrQueueFull`, `config.ErrNoToken`, `config.ErrInvalid`,
  `wbdevice.ErrNotConnected` и др.). Ошибки paho и go-telegram/bot наружу не
  выходят.
- Интерфейсы маленькие и лежат рядом с потребителем: ядро `bot` зависит от
  узких интерфейсов устройства и Telegram-клиента; моки для них — в `bot/mock`.
  Тестовые швы (часы, таймеры, паузы) неэкспортируемые.
- Журнал — глобальный stdlib `slog` в KV-стиле, настраивается один раз в `cmd`;
  `debug` из конфига поднимает уровень через `slog.LevelVar`.
- Тесты — stdlib `testing`, табличные, `t.Parallel()` везде; Telegram —
  `httptest.Server`, MQTT — встроенный брокер mochi-mqtt; сеть и контроллер не нужны.

### 7. Пакет и сборка

`debian/` по правилам Go-пакетов WB: `debhelper-compat (= 13)`,
`Build-Depends: golang-1.26-go:native`, `Architecture: any`, юнит
`wb-telegram.service` (`After=mosquitto.service`, `Restart=on-failure`,
`RestartSec=1`, `EnvironmentFile=-/etc/default/wb-telegram`,
`ExecStart=/usr/bin/wb-telegram $WB_TELEGRAM_OPTIONS`), `dh_installinit --noscripts`,
`dh_builddeb -- -Zgzip`. Бинарь — `CGO_ENABLED=0`, `-trimpath`,
`-ldflags "-s -w -X main.version=..."`. `make install` раскладывает файлы по
целевым путям (схема confed, модуль и пример wb-rules, конфиг по умолчанию —
conffile, каталог токена 0700; `override_dh_fixperms` сохраняет 0700).
`postrm` при purge удаляет токен.

Сборка — `scripts/build-deb.sh <arm64|armhf> [версия]`:
`dpkg-buildpackage -b -a<арх> -us -uc -d` в образе `golang:1.26-trixie` с
кросс-binutils; локально — `make deb` (Docker), в CI — тот же скрипт. Штатный
`wbdev gdeb` Wiren Board на macOS (Apple Silicon) не работает: amd64-образ
`contactless/devenv` под colima исполняется через qemu и падает на
`QEMU_CPU=cortex-a53`, а в окружении `gdeb` нет `golang-1.26-go` (Go 1.26 есть
только в sbuild-chroot для `cdeb`). `-d` пропускает проверку `Build-Depends`,
сами `Build-Depends` оставлены как у WB.

Поставка — GitHub Releases. Каждый push в `master`: тесты и линт, пакеты
`arm64` (WB8) и `armhf` (WB6/WB7, `GOARM=6`), релиз `v<мажор>.<минор>.<номер
сборки CI>` — мажор и минор из `debian/changelog`, патч растёт с каждой сборкой,
поэтому `dpkg -i` всегда обновляет. Версия пакета и бинаря одна (`VERSION`
передаётся в сборку). Установка и обновление на контроллере —
`scripts/install.sh`, опубликованный в релизе: определяет архитектуру через
`dpkg --print-architecture` и ставит пакет `wb-telegram_<арх>.deb` из последнего
(или указанного) релиза. Собственного apt-репозитория нет: для одного пакета
релизов и установщика достаточно.

Пакет собирается в окружении trixie, а контроллер работает на bullseye:
статический бинарь без shlibs-зависимостей и gzip-сжатие делают его
устанавливаемым на старом dpkg.

## Отступления от первоначального дизайна

1. **Повторы `getUpdates` делает библиотека** (пауза до 5 с, учитывает
   `retry_after`). Экспонента 1 → 60 с — только у собственных повторов бота:
   `deleteWebhook`, `setMyCommands` и отправка сообщений. Почему: опрос живёт
   внутри go-telegram/bot, заменять его — значит переписать библиотеку.
2. **«Связь восстановлена» пишется при первой следующей успешной операции**
   (апдейт или отправка), а не в момент восстановления сети: библиотека не
   сообщает об успешном опросе отдельно.
3. **Отправка при сбое сети и 5xx повторяется бесконечно** (1 → 60 с) до успеха
   или остановки, а не ограниченное число раз. `send/meta/error = "w"`
   выставляется после каждой неудачной попытки и снимается после успеха.
   Окончательно отвергнутые Telegram сообщения (4xx, кроме 401 и 429) не
   повторяются. Следствие: при обрыве голова очереди ждёт, новые сообщения
   копятся, переполнение выбрасывает самые старые — память ограничена очередью
   в 100 сообщений.
4. **Вкладки только у массива команд** (`_format: tabs` с `headerTemplate`
   `/{{self.name}} — {{self.description}}`); «Основное» и «Пользователи» — секции
   формы. Корневых вкладок у объекта в штатных схемах WB нет. Проверено на
   контроллере.
5. **Read-only статус токена — `"readonly": true`.** `options.wb.disabled` в
   редакторе confed не работает (поле остаётся редактируемым). Значение
   read-only поля форма возвращает в `fromJSON`, поэтому `-from-json` его
   отбрасывает.
6. **Список «Кому доступно» строится через `watch: {"users": "root.users"}`** и
   `enumSource` в таблице внутри элемента массива команд; новые пользователи
   появляются в списке без перезагрузки формы. Проверено на контроллере.
7. **`-to-json` читает конфиг со stdin, а не по пути.** confed вызывает крючки
   без аргументов и сам подаёт содержимое файла на stdin; пустой stdin — пустой
   конфиг. Если файла конфига нет, форма не откроется — поэтому конфиг по
   умолчанию ставится пакетом как conffile. Флаг `-config` нужен только сервису.
8. **Отдельной ошибки «бот выключен» нет**: `cmd` проверяет `cfg.Enabled` сам.
   **Уборка устройства** (`wbdevice.Purge`) работает без `ctx`, с собственным
   окном сбора retained-топиков (1 с) и таймаутом подключения.
9. **Порядок `deleteWebhook` → `setMyCommands` не гарантируется**:
   `deleteWebhook` идёт в фоне Telegram-клиента, меню команд ставит ядро
   параллельно. Функционально безразлично — меню не зависит от webhook.
10. **`WithInitialOffset` не используется.** Сообщения, отправленные боту, пока
    он не работал, Telegram отдаёт после запуска; выполнения устаревших команд
    не даёт проверка возраста по `message.date`, пользователь получает «устарела».
11. **Одноразовые контролы команд.** При каждом (пере)подключении бот публикует в
    `cmd_*` пустое значение, а не последний вызов; если публикация вызова не
    удалась, сохранённое значение сбрасывается, чтобы переподключение не
    повторило вызов, о котором пользователю сказали «не выполнена». Вторая линия
    защиты — модуль правил: он игнорирует пустые значения, вызовы старше 60 с,
    вызовы с `ts` раньше момента своей загрузки (с допуском 1 с) и повторные `id`.
    Так рестарт wb-rules вместе с переподключением бота в пределах 60 с не
    выполняет команду второй раз.
12. **Честная готовность при старте.** `meta/error = ""` публикуется последним —
    после уборки контролов удалённых команд и подписки на `send/on`; сервис
    ждёт первой готовности устройства (не дольше его таймаута). Готовность
    (`Connected`) истинна только после завершения публикации и подписки и
    сбрасывается при обрыве и перед каждой попыткой переподключения. Следствие:
    команды в первую ~1 с после старта получают «Контроллер недоступен».
13. **Остановка всегда ставит `meta/error = "r"`** и выходит с кодом 0: публикация
    `"r"` получает минимум ~1 с, даже если общий срок остановки истёк; если
    досылка очереди не уложилась в 5 с, остаток выбрасывается с предупреждением
    в журнале. Остановка при недоступном Telegram занимает до ~6 с (в пределах
    `TimeoutStopSec` systemd по умолчанию).
14. **Текст «Контроллер недоступен, команда не выполнена»** — дословно по
    дизайну, без имени команды.
15. **Записи в `/on` обрабатываются в отдельной горутине** через упорядоченный
    буфер, а не в обработчике paho, чтобы доставка в Telegram не блокировала
    MQTT-клиент. Буфер на 256 записей; при его заполнении приём снова ждёт;
    записи, оставшиеся в буфере при остановке, теряются.
16. **Пакет `internal/retry`** — общий расчёт пауз 1 → 60 с и ожидание с учётом
    `ctx` для `telegram` и `bot`, чтобы не дублировать логику.
17. **Сборка пакета.** `wbdev gdeb` на macOS (Apple Silicon, Docker через colima)
    не работает: amd64-образ devenv запускается через `qemu-x86_64`, а для wb8
    он выставляет `QEMU_CPU=cortex-a53`; кроме того, в окружении `gdeb` нет
    `golang-1.26-go` (Go есть только в sbuild-chroot для `cdeb`). Поэтому пакет
    собирается тем же `dpkg-buildpackage -b -aarm64 -us -uc -d` в контейнере
    `golang:1.26-trixie` под arm64; `-d` пропускает проверку `Build-Depends`, так
    как Go берётся из образа. `debian/rules` и `Build-Depends` не менялись —
    сборка штатным `wbdev` на Linux остаётся прежней.
18. **`postrm` вместо `postinst`**: каталог токена создаёт `make install`
    (в пакете он уже 0700), а `postrm` при purge удаляет токен и каталог.

## Последствия

- Новая команда — строка в настройках плюс правило wb-rules. Без правила
  пользователь получает «Команда /x отправлена, ответа от правил нет».
- Формат вызова и `send` — контракт между ботом, модулем `telegram.js` и
  README: менять их можно только вместе.
- Запись в `telegram_bot/send` при выключенном боте бросает исключение в
  wb-rules (устройства нет) — правила, которые должны работать без бота,
  оборачивают отправку в `try/catch`.
- Модуль правил считает возраст вызова по часам контроллера: перевод часов
  назад больше чем на 1 с после загрузки wb-rules отбрасывает новые вызовы до
  перезагрузки правил.
- Обрезка до 4096 символов считает руны, а Telegram — единицы UTF-16: текст у
  самой границы с символами вне BMP (эмодзи) Telegram может отвергнуть; такое
  сообщение не повторяется.
- Ожидающие ответа вызовы хранятся до часа (поздний `reply_to` доставляется);
  после этого ответ только пишется в журнал.
- Известные ограничения MQTT-слоя: запоздавший PUBACK после таймаута публикации
  может оставить retained-вызов, хотя пользователю ответили «не выполнена»
  (повтор отсекает модуль правил по `id` и возрасту); у токенов paho, брошенных
  по таймауту, не освобождаются message ID до переподключения; client ID уборки
  длиннее 23 символов (MQTT 3.1.1 гарантирует 23, mosquitto принимает длиннее).
- Тестовый брокер mochi-mqtt требует обходных приёмов: уникальные client ID
  наблюдателей и ожидание освобождения старой сессии при повторном подключении
  с тем же ID. mochi-mqtt и его зависимости попадают в `go.sum` только как
  тестовые.
- Версию релиза задаёт CI (`<мажор>.<минор>` из `debian/changelog` + номер
  сборки); локальная сборка без `DEB_VERSION` берёт версию пакета из
  `debian/changelog`, а бинаря — из `git describe`.
- Сервис зависит только от mosquitto и сети до `api.telegram.org`; при сбоях
  обоих восстанавливается сам, без перезапуска.
