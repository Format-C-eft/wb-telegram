# ADR 0001. Архитектура wb-telegram

Статус: принято. Базовая версия - v0.1.19 (`d9fbc5b`). Ниже также описаны
возможности текущей рабочей версии, ещё не входящие в базовую установку на
контроллере. Документ обновляется на месте; новые ADR не заводятся.

## Назначение и границы

`wb-telegram` передаёт команды между Telegram и MQTT на Wiren Board.
Пользователи и команды настраиваются через `wb-mqtt-confed`, прикладная логика
живёт в wb-rules. Новая команда требует настройки и правила, без пересборки бота.

В рабочем коде используются `github.com/go-telegram/bot` и
`github.com/eclipse/paho.mqtt.golang`; для тестов - mochi-mqtt и gomock.
MQTT Conventions реализованы в `internal/wbdevice` напрямую на paho.
Бинарь статический (`CGO_ENABLED=0`), загрузки Go-плагинов нет.

## Контракт Telegram и MQTT

Устройство называется `telegram_bot`. Каждой настроенной команде соответствует
текстовый контрол `cmd_<имя>`. Вызов публикуется с retained-флагом:

```json
{"id":"<update_id>","ts":<unix-время публикации>,"user":"<имя из настроек>","args":"<аргументы>"}
```

`id` связывает вызов с ответом, `ts` позволяет правилам проверить возраст вызова.
Возраст исходного сообщения Telegram проверяется отдельно по `message.date`.
При достижении `reply_timeout_s` команда из сообщения считается устаревшей.
Один обработчик публикует команды в порядке приёма. До 16 команд могут ждать
публикации. Срок проверяется повторно перед публикацией. Если MQTT не готов,
бот отвечает «Контроллер недоступен, команда не выполнена». Если брокер не
подтвердил уже начатую публикацию, бот сообщает, что результат неизвестен.

Правила пишут сообщения в `/devices/telegram_bot/controls/send/on`:

| Значение | Получатели |
|---|---|
| Обычная строка | Пользователи с флагом «Системные уведомления» |
| `{"text":"...","to":["имя"]}` | Указанные пользователи независимо от флага уведомлений |
| `{"text":"...","reply_to":"id"}` | Автор вызова; `reply_to` имеет приоритет над `to` |

Поле `id` сообщения игнорируется ботом; модуль правил добавляет его для
различения одинаковых записей подряд. При обработке сообщения правил текст сохраняется в
`controls/send`. CESU-8 от движка Duktape преобразуется в UTF-8 до разбора сообщения.
Plain text ограничивается 4096 единицами UTF-16 и обрезается с многоточием без
разрыва surrogate pair. HTML и MarkdownV2 не обрезаются: исходная строка длиннее
4096 единиц отклоняется до очереди. Caption фото ограничен 1024 единицами UTF-16.

Модуль `telegram.js` предоставляет `onCommand`, `cmd.reply`, `send` и `sendTo`.
При каждом подключении бот публикует `{}` в `cmd_*`, последний вызов не
воспроизводится. Правила игнорируют пустые объекты, повторные `id`, вызовы старше
60 с и вызовы до момента загрузки модуля с допуском 1 с.

## Правила: форматирование и кнопки

Режим разметки выбирается именем метода, а не пользовательским `options`:
`sendHTML(text)`, `sendMarkdown(text)`, `sendToHTML(users, text)`,
`sendToMarkdown(users, text)`, `cmd.replyHTML(text)` и
`cmd.replyMarkdown(text)`. Markdown соответствует MarkdownV2. Plain методы
`send`, `sendTo`, `cmd.reply` остаются без разметки. У текстовых методов
необязательный `options` содержит только `buttons`; поля `parse_mode`, `to`,
`reply_to` и `id` из него не принимаются. Обёртки сами назначают маршрутизацию и
уникальный `id`.

Модуль предоставляет `escapeHTML(value)` и `escapeMarkdownV2(value)` для
экранирования подставляемого обычного текста. Они не форматируют готовую строку
и не заменяют корректную разметку. Markdown helper рассчитан на текст вне
code/pre и URL.

Кнопка описывается подписью и настроенной командой с аргументами либо как
`{text, cancel: true}`. Допускается до 8 строк и 4 кнопок в строке, подпись до
64 единиц UTF-16, аргументы до 256 байт UTF-8. Клавиатуры разрешены только для
настроенных получателей в личных чатах. Действие проверяется по тем же правам,
что и обычная команда, при отправке и повторно при нажатии. Нажатие публикует
новый вызов `cmd_<имя>` с `args`, как прямой ручной вызов. `cancel` потребляет
панель без вызова команды. Первое допустимое нажатие потребляет все кнопки
панели; TTL - 5 минут. Максимум 1024 активных панели и 32 на пользователя;
после перезапуска процесса старые кнопки не действуют.

Кнопка добавляет `can_reply_ephemeral: true` к событию команды. Идентификатор
Telegram callback хранится только в памяти бота. Поле `ephemeral: true` в
ответе по `reply_to` позволяет один раз отправить текст или график нажавшему.
Бот отправляет короткие ответы через отдельную ограниченную очередь.
Дедлайн временного ответа - 13 секунд от получения нажатия. Таймер обычного
ответа на кнопку не срабатывает раньше этого срока. Временный график
принимается только при свободном построителе: клиент истории обрабатывает
один запрос одновременно. При занятости бот отправляет временное сообщение.

## Правила: карточка котла

`boiler_widget` принимается как ответ на `boiler_status`. Шаблон встроен
в бинарь, правило задаёт только `temperature` и `status`. Запрос
`widget_query` из личного чата повторно проходит проверку пользователя
и доступа к команде. Бот публикует обычный MQTT-вызов `cmd_boiler_status`
и связывает `reply_to` с запросом виджета. Новые показания возвращаются
через `answerWidgetQuery` и сохраняются в исходном сообщении через
`editMessageWidgetData`. Открытые карточки перерисовываются при
`chatDataChanged`. Для группы используется текстовый ответ.
MQTT-контролы и схема настроек используются те же.

## Правила: запрос графика

`cmd.replyChart(spec)`, `tg.sendChart(spec)` и `tg.sendChartTo(users, spec)`
публикуют запрос графика вместо текста. JSON-поля: `chart.title`,
`chart.period_s` и `chart.channels`; у канала используются `device`, `control`,
`label`, `unit`. Ответ содержит PNG и plain-text подпись. График нельзя
объединить с полями текста, `parse_mode` или `buttons`.

Построитель читает историю через MQTT RPC `wb-mqtt-db` 2.11.0. Разрешены 1-4
уникальных канала с одинаковой единицей измерения, период 60 секунд - 7 суток.
Подписи `title` и `label` ограничены 80 единицами UTF-16, `unit` - 16;
числовые значения по модулю выше 10^12 отклоняются. История не более 1000 точек
на канал и ответ RPC не более 512 KiB. Итоговое изображение 1000 × 600 пикселей,
до 2 MiB; общий бюджет PNG очереди доставки 16 MiB, сама очередь сохраняет
ограничение 100 сообщений. Очередь заданий графиков вмещает 8 заданий; один
получатель может иметь только одно выполняемое или ожидающее задание.

Пустая история даёт «За выбранный период данных нет». Если данные есть, но среди
всех точек нет числовых значений, возвращается «Канал не содержит числовых
данных». Ошибки RPC и построения сообщаются как отказ графика и не меняют
состояние связи с Telegram. Отсутствие или отказ истории не отключает текстовые
сообщения и кнопки.

Доступ к команде задаётся списком имён пользователей; пустой список разрешает
её всем настроенным пользователям. Неизвестный chat_id получает свой идентификатор
и сообщение об отсутствии доступа. `/start`, `/help` и обычный текст показывают
доступные команды. `/status` доступна получателям системных уведомлений.
Меню Telegram устанавливается отдельно для каждого пользователя.

Если правило не ответило за `reply_timeout_s`, бот сообщает об этом.
Повторные и поздние ответы доставляются, пока вызов хранится в таблице
ожиданий (до часа). После удаления вызова ответ только записывается в журнал.

## Telegram: соединение, очередь и состояние

Long polling принимает `message`, `callback_query` и `widget_query`.
Апдейты разбираются последовательно. Публикация команд и сетевые ответы на
кнопки выполняются через отдельные ограниченные очереди.
Webhook отложен без срока: для домашнего контроллера достаточно исходящего
соединения, а webhook потребует доступного Telegram HTTPS-обработчика,
сертификата и сопровождения входа через прокси, туннель или внешний сервер.
Long polling возвращает обновление сразу при появлении; таймаут опроса
не является задержкой доставки. Исходящий доступ к Bot API для отправки
сообщений требуется при обоих способах. Решение пересматривается при
конкретной потребности во внешнем приёме обновлений либо измеренной проблеме
long polling, которую решает webhook.

Таймаут подключения настраивается в диапазоне 5-120 с, таймаут опроса - 1-50 с;
оба по умолчанию равны 30 с. `http.Client` использует клон стандартного
транспорта, таймаут TCP/TLS и общий срок запроса «подключение + опрос + 10 с».
Проверка HTTP/2 посылает ping после `min(15 с, connectTimeout)` тишины;
ожидание ответа на ping и записи ограничено `connectTimeout`.

Обёртка `healthClient` считает связь восстановленной при новом соединении
или HTTP-ответе с кодом ниже 500, включая пустой ответ опроса, 401 и 429.
Ответы 5xx сбоем связи считаются, 429 означает ограничение частоты запросов.
Состояние связи и возможность отправить конкретное сообщение различаются:
например, 401 подтверждает доступность сервера, но приводит к остановке бота.

Очередь отправки ограничена 100 сообщениями; при переполнении выбрасываются
самые старые. Лимиты - 1 сообщение/с в чат и 30/с суммарно. Интервалы отсчитываются
после завершения HTTP-попытки, чтобы задержка первого запроса не приводила
к сближению следующих сообщений на стороне сервера.
Сетевые ошибки и 5xx повторяются с паузой 1-60 с до успеха или остановки;
429 ожидает `retry_after`. Прочие окончательные отказы 4xx не повторяются.
Голова очереди при сбое задерживает следующие сообщения.
`send/meta/error = "w"` отражает неудачную доставку и снимается после успеха.
Повторы `getUpdates` выполняет библиотека; `deleteWebhook`, `setMyCommands`
и отправку повторяют компоненты приложения. Установка меню и удаление webhook
идут параллельно, порядок между ними не гарантируется.

Служебные сообщения адресованы пользователям с «Системные уведомления».
Обрыв Telegram короче 30 с увеличивает только счётчик кратких обрывов в `/status`.
После 30 с сообщение о потере связи ставится в очередь; после восстановления
добавляется сообщение с длительностью и причиной. Доставка сообщения о потере
возможна после восстановления связи. Длительные обрывы учитываются за 24 часа,
краткие - с запуска. Журнал восстановления содержит длительность и число ошибок.
Потеря и восстановление MQTT сообщаются отдельно. Счётчики хранятся в памяти
и сбрасываются при перезапуске.

## Настройки и токен

Конфиг: `/etc/wb-telegram.conf`. Токен: `/etc/wb-telegram/token`, права 0600,
каталог 0700. Форма не получает сохранённый токен, журнал его не содержит.
Токен отделён от конфига, который confed передаёт в браузер.

Крючки формы получают данные на stdin:

- `-to-json` возвращает форму с пустым `token`, снятым `delete_token` и статусом
  наличия файла токена. Содержимое файла токена не читается.
- `-from-json` проверяет имена, chat_id, ссылки команд и токен, атомарно пишет
  или удаляет токен и возвращает конфиг без `token`, `delete_token`, `token_status`.
  Новый токен вместе с «Удалить токен» отвергается.

Ошибка крючка возвращается через stderr и ненулевой код выхода; confed не
сохраняет конфиг и не перезапускает сервис. Причина доступна в журнале confed.
Пустой stdin соответствует пустому конфигу; сам файл по умолчанию ставится пакетом.

В схеме вкладки используются только у массива команд. Статус токена имеет
`readonly: true`. Список доступа строится через `watch: {"users": "root.users"}`
и `enumSource`; обновляется при изменении списка пользователей.

## Компоненты и остановка

Пакеты `internal/`: `app`, `config`, `wbdevice`, `telegram`, `retry`, `bot`.
Компоненты реализуют `Run(ctx) error` и `Stop() error`; для завершения с общим
сроком используется `Shutdown(ctx) error`. Запуск: `wbdevice`, `telegram`, `bot`;
остановка в обратном порядке. При ошибке запуска ранее запущенные компоненты
останавливаются, ошибки остановки объединяются через `errors.Join`.

Конструкторы используют функциональные опции и `options.Validate()`.
Ошибки пакетов представлены `*Error` и сентинелами для `errors.Is`;
сторонние ошибки наружу не выходят. Интерфейсы определяет потребитель,
моки ядра лежат в `internal/bot/mock`. Логи идут через глобальный `slog`,
настроенный в `cmd`; уровень меняется через `slog.LevelVar`.

Готовность MQTT означает завершение публикации устройства, удаления устаревших
контролов и подписки на записи. `meta/error = ""` публикуется последним.
`Run` ждёт готовности в пределах таймаута с учётом отмены контекста.
Поколение соединения и блокировка публикации флага не позволяют устаревшему
`setup` снять ошибку после остановки.

| Ситуация | Результат |
|---|---|
| Бот выключен, токена нет или Telegram вернул 401 | Уборка MQTT-устройства, код 0, сервис inactive |
| Конфиг не читается или невалиден | Код 1, перезапуски systemd по `Restart=on-failure` |
| SIGTERM/SIGINT | Досылка очереди до 5 с, `meta/error = "r"`, штатный выход |

Уборка устройства удаляет retained-значения пустыми публикациями.
`Purge` использует собственный таймаут подключения и окно сбора топиков 1 с.
При штатной остановке устройство остаётся с флагом ошибки.
Публикация `"r"` получает минимум около 1 с даже при исчерпанном сроке остановки;
доставка через недоступный брокер не гарантируется. Недосланная очередь отбрасывается
с предупреждением. Общая остановка при недоступном Telegram занимает около 6 с.

## Сборка и поставка

`make build` собирает статический бинарь для Linux/arm64, `make deb` - пакет
через Docker в `golang:1.26-trixie`. Архитектуры пакета: `arm64` для WB8 и
`armhf` (`GOARM=6`) для WB6/WB7. `scripts/build-deb.sh` вызывает
`dpkg-buildpackage` с кросс-binutils и пропуском проверки Build-Depends (`-d`):
Go предоставляет образ. Рабочий способ сборки одинаков для локальной машины и CI.

Пакет использует debhelper 13, gzip-сжатие для старого dpkg, системный юнит,
схему confed, модуль и пример правил. Конфиг - conffile; `make install`
создаёт каталог токена 0700, `override_dh_fixperms` сохраняет права,
`postrm` удаляет токен при purge. Статический бинарь не требует shlibs-зависимостей.

В ветках CI требует тесты и линт изменений. В `master` тесты и полный линт
информационные и не блокируют релиз. Push с изменением только Markdown,
`docs/` или `LICENSE` не выпускает релиз. Для остальных изменений собираются
обе архитектуры и публикуется GitHub Release. Версия состоит из мажора и минора
`debian/changelog` и номера запуска CI; пакет и бинарь получают одну версию.
До 100 запусков `master` ждут завершения предыдущего запуска в очереди GitHub.
Поздно собранный релиз со старым номером не меняет `latest`. В остальных ветках
новый push отменяет устаревшую проверку.
Локально без `DEB_VERSION` пакет берёт версию из changelog, бинарь - из `git describe`.

Установщик `scripts/install.sh` выбирает архитектуру и скачивает пакет из
последнего либо указанного релиза. Обновление сохраняет пользовательский conffile
без интерактивного вопроса dpkg. Отдельного apt-репозитория нет.

Ответ истории ограничен 1000 точками на канал и 512 KiB. При превышении
пользователь получает «Слишком много данных: уменьшите период графика»;
первые точки молча не обрезаются. Подпись использует локальный часовой пояс
сервиса и явное смещение UTC. Русские названия и единица находятся в подписи
Telegram; на PNG ряды обозначены цветом и номером.

## Ограничения и проверки

- При выключенном боте записи из правил в отсутствующее устройство могут бросать
  исключение; независимые правила оборачивают отправку в `try/catch`.
- При отмене после постановки публикации в MQTT прекращается ожидание PUBACK.
  Правило могло уже получить команду. У неподтверждённых публикаций paho
  удерживает MQTT message ID, пока соединение не обработает подтверждение
  или клиент не будет пересоздан.
- Записи MQTT передаются обработчику отдельной горутиной через буфер 256 записей;
  при переполнении отбрасывается новая запись с предупреждением в журнале.
  При остановке остаток очереди теряется.
- Telegram отдаёт накопленные обновления после запуска; бот проверяет возраст
  команды, а не сбрасывает очередь через `WithInitialOffset`.

Тесты используют stdlib `testing`, `httptest.Server`, встроенный брокер mochi-mqtt
и gomock. Проверки разработки: `make test`, `make lint-full`, `make build`.
